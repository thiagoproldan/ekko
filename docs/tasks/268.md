--clear and --restore can lose an item: write the destination before the source, so a failure leaves a duplicate, never a loss

Re-verified 2026-09-21 at 470edb7 on a scratch board: one done task, the archive folder made read-only, ekko --clear answers 'Permission denied', and the task is in neither storage.json (0 items) nor archive.json (0). delete_items_locked (src/ekko.rs, used by --clear) saves storage and then the archive; restore_items saves the archive and then storage. Fix: --clear writes the archive first and storage second, --restore storage first and the archive second, so a failure in between leaves the item in both places, which a second --clear or --restore resolves, instead of nowhere. Test: the unwritable-archive setup keeps the task in storage. From handoff 266, reproduced there as well.
