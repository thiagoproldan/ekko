# 276. The lock-timeout message tells the user to delete the lock file, which under flock lets a second writer in

*Task · done · medium priority · created 2026-09-21 · [history](../history.md)*

src/storage.rs:71 ('If no other ekko process is running, delete this file and try again'), shown by src/render.rs. Under flock, deleting .lock makes the next process lock a new inode while the holder keeps the old one: two writers, the lost update tests/concurrency.rs exists for. Fix: name the holder (the inode in /proc/locks, or fuser) and say to end that process or wait; never suggest deleting. From handoff 266; re-verified at 470edb7. A blocking flock (task on lock waiters) also makes the timeout rarer.

Done 2026-09-21, uncommitted: a timeout names the holder from /proc/locks, confirmed by that process having the lock file open, e.g. 'held by process 516519 (flock -x ... sleep 8)', and says to let it finish or end it if it is stuck, never to delete the lock file; CLI, MCP and --json alike. Found on the way: on btrfs, /proc/locks gives the superblock's device (00:23) where stat gives the subvolume's (0x25), so the lookup matches the inode and checks the process's open files rather than the device.
