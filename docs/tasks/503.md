### <a id="641"></a>641. DESIGN for 503, 2026-09-25, session on pts/0, from gotcha 498, question [502](../notes.md#502), src/storage.rs and src/project.rs. Nothing…

DESIGN for 503, 2026-09-25, session on pts/0, from gotcha 498, question [502](../notes.md#502), src/storage.rs and src/project.rs. Nothing built yet.

AT RISK. A project's board is all in &lt;root>/.ekko/: project.json (the marker: name and id), storage/ (storage.json, 970 KB on ekko; counters.json; journal.jsonl), archive/ and history/ (46 MB on ekko). Only .git/info/exclude keeps it out of git. git clean -fdx, removing the folder, or a fresh clone takes all of it. ekko in that folder then finds no marker and falls back to the default board without a word; ekko init there makes a new, empty project, and registering it drops the old one from the registry.

(1) THE COPY

- Where: \~/.ekko/copies/&lt;project id>/, beside the registry and the trash. By id, which never changes: a moved project keeps its copy, and a new project in the same folder gets its own.
- What: the board's current files -- project.json, storage.json, counters.json, journal.jsonl, archive.json. Not history/: that is the undo, and the copy is for a lost folder.
- When: at every write, in Storage, under the board's lock, right after each file's rename. A hard link where it can: it costs nothing, and since ekko replaces a file by rename and never writes one in place, a linked version never changes. A copy where it cannot: /home and /projects here are separate btrfs subvolumes, where a hard link fails (EXDEV, tried) and a reflink works; std's fs::copy goes through copy_file_range, which btrfs turns into a clone. On a filesystem without clones, \~1 MB per write, as much as the write itself. Best effort, like history: a failed copy never fails the write. The default board, already in \~/.ekko, gets none.
- How many: one, the latest. Older versions are history's job, once task [640](640.md) fixes its daily versions.
- Restore: ekko init in a folder with no board, for a registered project that is missing -- its registered folder, or any folder whose name (or --name) is the project's, as when a repo is cloned again elsewhere -- restores that project from its copy, same id and name, instead of making an empty one, and says so with the copy's date. It extends what init already does to find a moved project. --destroy afterwards if an empty board was wanted.
- Warning: in a folder the registry lists for a missing project, the prime says the board is gone and that ekko init restores it, instead of showing the default board without a word.

(2) A MISSING PROJECT. --projects stays read-only and prints the way out under it: ekko init in its folder, when a copy exists; ekko --project &lt;name> --destroy, to forget it. --destroy on a missing project, which fails today with no folder to move, drops it from the registry and moves its copy, if any, to \~/.ekko/.trash/.
