# 862. ekko: a conversation continued in a background session loses its holds

*Task · done · medium priority · created 2026-09-27 · [history](../history.md)*

Measured 2026-09-27, 16:01-16:30 (-03).

What happened:

- Claude Code 2.1.283 moved conversation 33fb3219 out of the terminal. The terminal's process is pid 1047920, the `claude` wrapper on pts/0, started 02:50.
- A daemon took the conversation over: `.claude-unwrapped daemon run --origin transient --spawned-by {pid 1047920}`. It runs `.claude-unwrapped --session-id a7ab82f1 --fork-session --resume <33fb3219.jsonl> --reply-on-resume --name "Continuando (2)"` on pts/3.
- The old transcript ends with {"type":"continued-in","continuedInSessionId":"a7ab82f1-..."}.
- SessionStart fired with source fork.
- In the same second the daemon started a third session: 4131070b on pts/4 (`--agent claude --inherit-permission-mode bypassPermissions`), with no transcript under this project.

What ekko did:

- It still counts 811's holder as running: process 1047920, conversation 33fb3219.
- So the continuing conversation's set_state done on 811, its own task, was refused HELD.
- ekko --sessions lists 33fb3219 (holding 811), a7ab82f1 and 4131070b as three running sessions.

What ekko could do: take a conversation that continues another as the holder's own, the way a resumed conversation already takes back what it held. The continuation is readable from the old transcript's continued-in record. The SessionStart input may also name the parent session under source fork; not checked yet.

Check first: what the SessionStart input carries under source fork, and whether process 1047920 still hosts the conversation or only launched it.
