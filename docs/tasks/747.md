# 747. Auto mode for the reset: a session running alone hands off and goes on by itself

*Task · done · created 2026-09-26 · [history](../history.md)*

Asked by the user, 2026-09-26 \~01:15 (-03), going to sleep with a session left to run: 'auto mode para ekko reset, no sentido de para não travar longas sessions que estão rodando sozinhas é bom ter esse auto mode que pode ser ativado e desativado'. A switch, on and off.

Today the reset needs a person: past the threshold ctx's Stop hook asks for the handoff, and only the user's /clear and 'continuando' start the fresh session. A session left alone stalls there, or keeps working and pays for an ever larger context. Session 83c87811 is the case: ctx at 175k with the handoff flag up, left on overnight to watch 259's runs.

Known: evals/paired/harness.py does it headless (past T a PostToolUse hook asks for the handoff, then the harness starts a new session told 'continuando'), which an interactive session cannot copy as is. Claude Code's own --autocompact is the other road, and task [259](259.md) measures it against the handoff (cell B against C): its result says which one the mode should drive. TO DESIGN: how the switch is flipped (a command, ctx's state, per session or global), and how an interactive session gets its /clear with nobody at the keyboard.

KEEP THE HANDOFF (the user, 2026-09-26 16:19, reading 259's result): the handoff is what carries context from one session to another, so the mode must not remove it. What 259 measured (notes [752](259.md#752), [753](259.md#753)): writing the handoff is cheap, \~0.11M a reset; the dear part of a C reset is the fresh session finding its way again, \~0.44M. So the mode can let the compaction replace only the /clear and 'continuando' between resets inside one long run, and still have the session write its handoff on the board when it stops or ends, for the next session, another profile, a return days later, and the user.

NO SWITCH (the user, 2026-09-26 \~16:45): no mode to turn on and no command to remember before opening Claude Code -- the real use is typing 'claude' in a folder and working, and a switch used in rare cases is forgotten exactly when it is needed. So one behaviour, set once in \~/NixOS, covering both cases. A direction to test, not built: (1) the handoff ask stays at 250k as today; (2) the session tells a present user from an absent one by itself, by the time since the user last typed (ctx's UserPromptSubmit hook sees each prompt): present, the ask ends the turn for a /clear as now; absent for N minutes, the ask says to write the handoff and go on; (3) Claude Code's compaction as a safety net a little above the handoff threshold (--autocompact \~T+33k, autoCompactEnabled on in both profiles), which only fires when no /clear came. To check first: whether a background task's notification fires UserPromptSubmit (it arrives as a user message, and must not count as the user typing); and the compaction's quality at \~250-280k, since 259 measured it at 160k.

FIRST CHECK DONE, 2026-09-26 (the gotcha beside this task): UserPromptSubmit fires for background notifications too, so presence cannot be read off it; the transcript's origin.kind can, 'human' against 'task-notification' and 'auto-continuation'. Point (2) of the direction becomes: at ctx's Stop hook, which already reads the transcript, the time since the last row with origin.kind 'human' says whether the user is there. Left to check: the compaction's quality at \~250-280k.

THE USER'S OWN DESIGN (2026-09-26 \~17:15): it was always the ritual itself made automatic -- ctx asks for the handoff, then clears and sends 'continuando' by itself -- not a compaction. It can be done in the user's terminal, Konsole (no tmux), checked read-only from inside session 83c87811: Konsole exports KONSOLE_DBUS_SERVICE and KONSOLE_DBUS_SESSION (:1.80, /Sessions/1) into the shell, so every Claude Code hook inherits the address of its own tab; that session object has sendText(s) and runCommand(s), and foregroundProcessId answered 119828, the Claude Code process itself, so a hook can check it types into its own session before typing (busctl --user call "$KONSOLE_DBUS_SERVICE" "$KONSOLE_DBUS_SESSION" org.kde.konsole.Session sendText s '...'). The path: once the handoff is written and the turn has ended, a process ctx leaves behind checks the foreground process, types /clear and Enter, waits for the new session's SessionStart, then types 'continuando' and Enter. NOT TRIED: typing into Claude Code's prompt this way (whether Enter submits, the timing after the Stop hook, what happens to text the user is typing at that moment); try it on a scratch Konsole tab first. The compaction stays only as a safety net for a tab that is not Konsole. Other terminals would need their own way in (tmux send-keys, kitty @ send-text, wezterm cli send-text).

Defect in ctx 0.4.0, found by the end-to-end test on 2026-09-26 \~18:16 (-03), after the deploy (614be79, system 7z61nzw4): bin/auto-reset never types when a prompt suggestion is in the box (the gotcha beside this note).
