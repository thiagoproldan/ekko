# 389. Waiting on another session: tell it when what it waits on is free

*Task · done · created 2026-09-22 · [history](../history.md)*

A session that depends on a task or an action another session holds is told when it is free, instead of watching the board itself. THE USER, 2026-09-22, who wants it as a future feature: 'hook de task entre sessions de agents, quando vc depende de alguma task ou ação no ekko mas está preso a outro agent e session'.

SEEN 2026-09-22. Session a6b026e6 had the fix for task [380](380.md) ready to land, but session e3011485 (pts/0) had claimed release 388 (v0.15.0), and procedure [382](../procedures.md#382) item 3 allows one release at a time. So a6b026e6 waited with a loop it wrote by hand: jq over storage.json every 10 seconds until 388 was done, then it would rebase, test and push. Nothing in ekko modelled the wait. The other session did not know anyone was waiting on it, the user could not see it in ekko --sessions, and the wait lived only in that session's background shell, lost on a /clear or restart. It is the same shape as the questions of note [357](../notes.md#357): coordination held in one session's head.

WHAT EXISTS TO BUILD ON. blocked_by links tasks, but across sessions it says nothing about who holds the blocker. HELD refuses a change, but the refused session has no way to wait. heldBy and doneBy name the sessions. changes with a cursor tells what moved. The FileChanged hook on storage.json already runs in every session, for the task list.

TO DESIGN. How a session says it waits: on an item reaching a state, a task leaving another session's hands, or a question being answered. Where the wait is kept: on the board, so it outlives the session, names who waits, and shows in the holder's prime and in ekko --sessions. How the waiting session learns the wait is over: in its next tool reply, through the FileChanged hook if a hook's output can reach an idle session, or by waking it through Claude Code's own mechanisms. And whether the holder sees who waits on it, so it can hurry or hand the work over.

## Notes

### <a id="619"></a>619. DESIGN, proposed 2026-09-24 by the session on pts/5, for the user's approval (the questions attached here).

VERIFIED FIRST: a hook can wake an idle Claude Code session. In 2.1.282 a command hook takes asyncRewake: it runs in the background and, on exit code 2, wakes the model with rewakeMessage and the hook's stderr in a system-reminder, and shows rewakeSummary to the user (both of those marked @internal in Claude Code's schema; without them the text still arrives, as 'Stop hook feedback'). The test used a FileChanged hook with asyncRewake on one file and a headless session whose stream-json input counts as interactive. The session sat idle after its first reply. Writing the file ran the hook within 1 s, and the session ran a second turn on the hook's message. The hook's input holds session_id, hook_event_name, file_path and event.

THE WAIT, ON THE BOARD: a note of a new kind attached to the item waited on, as a question is. It records who waits (the session, as a claim records it: process and conversation) and until what. There are three conditions. done: the task closes, and the waiter is told whether it was done or cancelled. free: the task leaves another live session's hands. answered: a question gets its answer. The note's text says what the waiter will do then. It is required: the holder reads why, and a session woken after a /clear knows what to do. A new MCP tool, wait, records the note (item, until, text; cancel drops it). A wait already met records nothing and says so.

OVER: every write re-checks the open waits. When one is over, the write records on the note when, by whom and in what state, so the note becomes history as an answered question does. The writer's reply names who waited and says they are told.

TOLD, ONCE: (a) In Claude Code: the plugin gets a second FileChanged hook on storage.json, ekko --waits --hook, with asyncRewake. It wakes the waiting session with what happened and the text the session gave. (b) In any MCP client: the waiter's next ekko reply carries a notice, and its prime lists 'Waits over, for this session', as it lists answers. (c) After a restart: the resumed conversation's waits are its own again, as its questions are. The record of what was told stays outside the board, since reading the board writes nothing to it. It is kept in the XDG state directory: one marker per session and wait, created exclusively, so two hook runs cannot both wake the session.

IMPLICIT: a question a session asked is already a wait on its answer. An answer given in another terminal wakes the asker the same way.

SEEN BY: the holder (the wait under its task in the prime, in context, and once in its next reply); the user (ekko --sessions: waiting on, waited on by); and a HELD refusal, which names wait as the way to be told when the task is free.

NOT NOW: a blocking ekko --wait for clients without such a hook (495's verdicts decide it). A holder's process ending without a write is seen only at the next write.

BUILT and released as v0.21.0 (note [626](#626)), with the user's three answers (620-622). Nothing here is left to propose: the NOT NOW items stay with 495's verdicts, and the headless limit is gotcha [624](../gotchas.md#624).
