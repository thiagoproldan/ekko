# 263. A cursor never runs ahead of the board it came with. save_against writes counters.json (the revision) before…

*Task · done · medium priority · created 2026-09-21 · [history](../history.md)*

A cursor never runs ahead of the board it came with. save_against writes counters.json (the revision) before storage.json, and readers take no lock, so prime, changes, if_rev, the resume hook and the resources server's list_changed can pair revision N+1 with board N. The N+1 changes are then never listed. Reproduced 2026-09-21 with 0.10.2: an MCP client followed changes, always passing the cursor the last reply returned, while ekko --task wrote 100 tasks on a copy of this board. It never saw 88% of them polling every 5 ms, 21% every 20 ms and 6% every 100 ms: a window of about 6 ms per write. Fix: read the revision and the board under a shared flock; or write storage, then the journal, then counters, read the revision first, and heal a crash by taking the highest revision any item carries. Add the race to tests/concurrency.rs. From the review of 2026-09-21 (bug 1).

## Notes

### <a id="288"></a>288. Measured and fixed in a prototype, 2026-09-21, not applied…

Measured and fixed in a prototype, 2026-09-21, not applied: target/evals/analise-final/fixes-cursor-order-heal-flock.patch, which applies to 470edb7. A session following changes, passing the cursor each reply returns, while another MCP server creates 200 tasks: missed 100% polling back to back, 47.5% at 5 ms, 13% at 20 ms, 2.5% at 100 ms. Under continuous writes 193 of 400 primes (48%) handed out a cursor ahead of the board they showed, so prime(if_rev) then answers unchanged over a write the session never saw. And --clear's removals were missed 60 of 60, because the journal is appended after the revision is published. Cause, in the code: save_against writes counters.json first, and prime and changes read the board before the revision.

Fix: publish last, read first. A write goes storage, then the journal, then counters; a read takes counters (R), then the board and the journal, and changes lists only revs in (since, R]. Why it is exact: counters = R is renamed after the board and the journal entries up to R, and the reader reads those after reading R, so every change up to R is visible to it; a change above R waits for the next call, whose since is R; cursors never decrease, so each change is listed once. Results: 0 missed in 2,400 writes (12 runs, \~45,000 changes calls), 0 listed twice, 0 primes ahead (126 of 400 behind, which only repeats), 60 of 60 removals reported. set_phases must also write phases.json before counters. A crash between storage and counters leaves items a revision ahead of counters until the next write, which the healing rule settles (counters task on @analise-final-ekko): under 300 SIGKILLs, no torn file and no acknowledged write lost. The patch adds a regression test to tests/concurrency.rs that fails at 470edb7 (missed 40 of 40) and passes with the fix; 269 tests and clippy pass. It loses data silently for any session that follows changes: raising this to priority 3 is recommended.
