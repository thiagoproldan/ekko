# 845. ekko: an enum variant this version does not know makes the board unreadable

*Task · done · created 2026-09-27 · [history](../history.md)*

MEASURED 2026-09-27 \~03:40 (-03), while fixing 829, with the build that fixes it, on a copy of the ekko board (838 items) in a scratch HOME (/tmp/829/enum). I set one item's knowledge to "lesson", a variant no version has yet. Then `ekko --list pending` and `ekko --task` both failed with "unknown variant `lesson`, expected one of `decision`, `gotcha`, `procedure` at line 18258 column 25". The file was left as it was, with the variant still there.

So nothing is lost: the older ekko refuses the whole board rather than dropping the value. But every command and the MCP server fail until the older ekko is upgraded, over one item. Until and How derive the same way (read, not run), so a new wait kind or way of ending would do the same.

829 made every struct keep the fields it does not know, but a value inside a known field is a different case. Options, not settled: a catch-all variant that keeps the string (#[serde(other)] keeps no data, so it would need a hand-written Deserialize); or the rule that a new variant ships with a reader one version ahead, as 829's fix did for fields. A test in the style of 829's would plant an unknown variant in each enum and require the board to read and write it back.
