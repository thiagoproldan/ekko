## Notes

### <a id="900"></a>900. Design for 897, from how others move items between containers (2026-09-28):

- GitHub transfer: comments and assignees kept, labels and milestones only if the target has them, new number, old URL redirects (docs.github.com, "Transferring an issue").
- Jira move: new key, old keys redirect (stacked, if moved again), sub-tasks go with the parent, a status or required field the target lacks must be mapped.
- Linear move to another team: new identifier; team-scoped labels may not carry over.

ekko's version, as `ekko --move-to <PROJECT|FOLDER> IDS` (CLI; MCP left out, since cross-board MCP writes go through links, and the default board links to nothing):

1. The item keeps uid, dates, createdBy, state, holders, boards and text, and takes the next display id there. Text is not rewritten ("#12" keeps saying 12); the reply maps old id to new.
2. A task takes every note attached to it, trashed ones included. A note attached to a task moves only with it.
3. Every uid one item holds of another (blockedBy, attachedTo, supersedes, wait.on, cue.question, question.cue.gotcha) must stay on one board: a link between an item that moves and one that stays is refused, naming both. The board would otherwise drop it silently: a blocker that is not there does not block, an older decision becomes current again.
4. Revisions are per board: rev, question.rev, answer.rev, wait.rev and over.rev are restamped by the destination's write.
5. A phase must be declared at the destination.
6. A cue that is on keeps what it guards: an absent folder is pinned to the source's (a project's folder, or / from the default board). A session cannot move one at all (CUE_IS_USERS, task [805](805.md)).
7. What a running session watches here stays unless --force: a task it holds, an open wait, a question it asked with no answer yet. Its wake hook watches this board's file only.
8. The destination is written first, then the redirect, then the source. A retry finds the item already there by uid and does not add it twice, as --restore does.
9. The source keeps moved.json: one entry per id that left, with its uid, where it went and its new id. A lookup of the old id answers MOVED; one by uid, the last time it left. changes reports it as moved, not removed. An item that comes back keeps the redirects it left, stacked as Jira stacks keys; pruning them lost history in both lookups and changes.

The every-field rule is enforced by exhaustive destructuring of Item and its nested structs, so a new field does not compile until it is classified.

Shipped in ddb73f4 (not released). Tests: 10 unit tests in src/move_to.rs, a moved.json round trip in storage.rs, and one CLI test. 20 unit mutations and 3 CLI mutations each failed at the expected check (procedure [876](../procedures.md#876)).

### <a id="905"></a>905. 897 -- cues ligadas que mudam de quadro. Uma cue sem pasta guarda o escopo do quadro onde está: a máquina toda no…

897 -- cues ligadas que mudam de quadro. Uma cue sem pasta guarda o escopo do quadro onde está: a máquina toda no quadro padrão, e só a pasta do projeto num projeto. Por isso, ao sair do quadro padrão, a cue é gravada no destino com folder "/" (a máquina toda) e continua guardando o mesmo que antes. Ao sair de um projeto, leva a pasta dele. Uma cue que já tinha pasta própria fica como está. Mantenho?

Options:

- Manter: A cue continua guardando o que guardava
- Adotar o escopo do destino: A cue sem pasta passa a guardar só a pasta do projeto de destino

**Answer**, 2026-09-28: o que é um cue?

### <a id="907"></a>907. 897 -- ferramenta MCP move_to (você pediu CLI e MCP). No GitHub e no Jira, só move quem tem permissão nos dois lados. O…

897 -- ferramenta MCP move_to (você pediu CLI e MCP). No GitHub e no Jira, só move quem tem permissão nos dois lados. O GitHub exige acesso de escrita no repositório de origem e no de destino. O Jira exige 'Move issues' no projeto de origem e 'Create issues' no de destino. No ekko, o que dá a uma sessão permissão em outro quadro é o link entre projetos. Só que o quadro padrão não se liga a nenhum, e o caso que abriu a 897 é justamente levar itens do quadro padrão para um projeto. Como a ferramenta deve chegar lá?

Options:

- Link + liberação única (recomendo): Entre quadros ligados, move direto. Para um quadro sem link, incluindo o padrão, a chamada é recusada com um código. A sessão te pergunta pelo ask (allow), e você libera aquela movimentação uma vez no menu do ekko. É o mesmo caminho que a trava de gotchas já usa para comandos Bash.
- Só entre quadros ligados: Como no GitHub e no Jira. O quadro padrão continua só pela CLI, então o caso da 897 ainda exige a CLI.
- Ligar o quadro padrão a projetos: O quadro padrão passa a aceitar link, e com ele a opção anterior cobre tudo. Mas o link libera todas as escritas nos dois sentidos, não só a movimentação.

**Answer**, 2026-09-28: Link + liberação única (recomendo)

### <a id="908"></a>908. 897 -- de novo a pergunta das cues, agora com a explicação. Uma cue é a trava presa a uma gotcha. A gotcha descreve uma…

897 -- de novo a pergunta das cues, agora com a explicação. Uma cue é a trava presa a uma gotcha. A gotcha descreve uma armadilha. A cue diz qual comando Bash ela barra: o comando, as palavras que ele precisa ter e a pasta onde vale. Depois que você liga a cue no menu do ekko, o hook PreToolUse recusa esse comando nas sessões do Claude Code, e o motivo que aparece é o texto da gotcha. Exemplo: a 841 quer uma cue que recuse `cargo fmt --all` na pasta do winwayland. Uma cue sem pasta vale no escopo do quadro em que está: na máquina toda, se o quadro for o padrão; só na pasta do projeto, se for um projeto. Quando a cue vai do quadro padrão para um projeto, eu gravo folder "/" nela, e ela continua valendo na máquina toda. Quando sai de um projeto, leva a pasta dele. Se a cue já tinha pasta própria, não muda. Mantenho?

Options:

- Manter: A cue continua barrando onde barrava
- Adotar o escopo do destino: A cue sem pasta passa a valer só na pasta do projeto de destino

**Answer**, 2026-09-28: Manter
