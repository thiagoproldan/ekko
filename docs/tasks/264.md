### <a id="289"></a>289. Two agents on one board, measured 2026-09-21 with two MCP servers (target/evals/analise-final/scripts: agents.py…

Two agents on one board, measured 2026-09-21 with two MCP servers (target/evals/analise-final/scripts: agents.py, contention.py): what holds, what breaks, and what owners can build on.

HOLDS: 240 concurrent creates from 4 servers all landed, no id or uid repeated, no torn file; 300 SIGKILLs mid-write lost no acknowledged write.

BREAKS: (1) B sets progress on the task A is working and gets the same bare ok (261). (2) B's next then ranks A's task first, as in progress: a second session is steered into the first one's work. (3) Each prime shows the newest handoff on the board as where the last session stopped, the other session's included (262). (4) Whole-value writes drop the other's change (task on @analise-final-ekko). (5) The cursor race (263).

WHAT OWNERS CAN BUILD ON: every ekko --mcp server already carries CLAUDE_CODE_SESSION_ID and CLAUDE_CONFIG_DIR in its environment (read from /proc for the four servers running during the analysis), so a claim can name the session and the profile with no new protocol, and hooks receive session_id too. Liveness with no clock: each server holds a flock on .ekko/sessions/&lt;session id>.lock for its lifetime, and a claim is live exactly while that file is locked; the kernel releases it when the process ends, the argument storage.rs already makes for the board's lock, and it avoids the expiring-lease trap (Kleppmann 2016: a paused holder outlives its lease without knowing, hence fencing tokens). A claim is taken in the same draft as set_state progress, atomically, as Beads does with bd update --claim; another live session's claim is refused as HELD or at least reported; next and prime leave other sessions' live claims out of what to take up and list them apart.
