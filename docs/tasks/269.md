A lost or older counters.json sends the revision back and hides every later write from cursors already held: heal it from the items

Reproduced 2026-09-21: 5 creates, a prime (cursor 6), counters.json deleted, 3 creates; changes(6) answers 'cursor 3 · 0 changed since 6': the three writes are never listed and the cursor went back. A storage.json restored from a backup, a sync tool or a hand copy does the same, and evals/agent's copy_real does it by accident (eval-hygiene task). Fix, validated in target/evals/analise-final/fixes-cursor-order-heal-flock.patch: a write takes revision = max(counters.revision, the highest rev any item carries) + 1, the way highestId is already healed from the ids, and changes answers a cursor ahead of the board's revision as incomplete (prime again). With it the same steps answer 'cursor 9 · 3 changed since 6'. Under 300 SIGKILLs mid-write, the next clean write always left the revision at or above every item's rev, and its own rev unique.
