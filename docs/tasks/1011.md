# 1011. add_boards takes an item off My Board when no remove_boards is given

*Task · done · medium priority · created 2026-10-01 · [history](../history.md)*

MEASURED 2026-10-01 00:23: update item 192 with add_boards ["private"], through the MCP server (0.29.0, the same ops.rs as 0.30.0). Before it, 192 was on ['My Board'] in every backup in .ekko/history; after it, on ['@private'] alone.

CAUSE (src/ops.rs, Batch::update): removed = boards(&spec.remove_boards), and boards() of an empty list returns the default board, ['My Board']. So every update that adds a board with no remove_boards takes My Board off. The add side had a guard for the same fallback; the remove side had none.

MISSED BY adding_and_removing_commute_and_a_stale_read_is_refused, which adds x, then adds y removing My Board, and checks only the end: ['@x', '@y'] either way.

### <a id="1013"></a>1013. FIXED, uncommitted, 2026-10-01 \~00:35.

- A new helper, named(), names the boards in add_boards and remove_boards with no fallback to the default board. boards() keeps that fallback for an item's own list, so taking off the last board still leaves the item on My Board.
- The add side's guard against the fallback went with it.
- TEST: adding_or_removing_boards_keeps_every_board_not_named enumerates each way an update changes boards: add, add one already there, remove, remove the default board, remove a blank name, add and remove together, remove all. With the old removal it fails on the first case, ['@a', '@b'] instead of ['My Board', '@a', '@b'], the defect as measured.
- THE BOARD: item 192, which the bug took off My Board, is back on it beside @private.
- Until a release with the fix reaches the MCP server, put a board beside the others with update's boards, the whole list, not add_boards.
