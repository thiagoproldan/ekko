# 352. Two sessions on one repo: agree how work lands on main, so no session waits on another's working tree

*Task · done · medium priority · created 2026-09-22 · [history](../history.md)*

SEEN 2026-09-22, the first conflict between two sessions working at once. Session dccf828e worked in a worktree on branch auditoria; session 9e449e1b worked directly in main's working tree. To merge, dccf828e needed main's tree while 9e449e1b was editing it (273), so it asked the user who should merge. By the time the user read the question, main had moved three commits (273, 277, v0.13.0) and the question no longer fitted: auditoria no longer fast-forwarded. The same day, 9e449e1b rebuilt its unpushed main to get past the gh token's missing workflow scope, which a branch built on those commits would have had to untangle. Nothing was lost; the cost was a blocked session and a stale question to the user.

PROPOSED, for the user to approve; approved, it becomes a procedure the prime lists:

1. No session develops in main's working tree. Each works in its own worktree on its own branch (git worktree add), as dccf828e did; main's tree only follows origin, with git pull --ff-only.
2. Work lands by fast-forward from the branch: rebase onto origin/main, cargo test and clippy, then git push origin HEAD:main. A rejected push means main moved: rebase and push again. Never force a push to main, never rewrite what is pushed.
3. One release at a time: a session claims it by setting a task 'Release vX.Y.Z' in progress; from 0.13.0 a second running session gets HELD.
4. Tasks are claimed with set_state progress, which from 0.13.0 records the holder, rather than with 'Held by' text; when two sessions run, the first to start writes the split in its task, as 312 did.
5. A question to the user about another session's state names the commit it was asked against, so an answer that comes later can tell it is stale.

THE USER, 2026-09-22: items 1 to 4 approved; item 5 set aside, since it belongs to the wider question of several agents handling one ekko (the multi-agent task this now waits on, and the note on questions). To become a procedure after that work, not before.
