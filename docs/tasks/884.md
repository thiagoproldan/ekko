### <a id="886"></a>886. Redis-style cache, weighed 2026-09-28 at the user's question ('estava pensando no estilo redis de cache, mas não sei se…

Redis-style cache, weighed 2026-09-28 at the user's question ('estava pensando no estilo redis de cache, mas não sei se encaixa'). Analysis, not yet a decision:

- The in-memory part already exists per process: storage.rs keeps each parsed board keyed by the file's version (dev, inode, mtime, size) and re-parses only after another process wrote (BOARDS, BOARDS_KEPT = 8); since 859 a write keeps the map it wrote.
- A Redis server does not fit: a daemon to install and keep up, beside a file that stays the truth, so two copies to keep in step. It pays off when many clients hit a slow store over a network; here a handful of local processes read one 1.5 MB file (.ekko/storage/storage.json).
- ekko's cost is tokens more than milliseconds, and a server-side cache does not touch tokens. The cache that does is a 'not modified' answer, as HTTP's ETag/304: prime's if_rev already answers in one line when nothing moved; context and search could take the same.

CORRECTED the same day: the last point assumed sessions re-read items; measured, they do not (decision on 884), so no 'not modified' answer is built.
