### <a id="338"></a>338. THE PROPOSAL, from a conversation with Claude Opus 5.5 in Claude Desktop, pasted by the user on 2026-09-22 ('ekko seria…

THE PROPOSAL, from a conversation with Claude Opus 5.5 in Claude Desktop, pasted by the user on 2026-09-22 ('ekko seria uma memoria de longo prazo melhorada para o claude code?'). Three principles as the filter: a read never writes, nothing is captured behind the user's back, the machine does the mechanical and Claude the judgment. Seven ideas from cognitive science:

(1) Semantic memory by retrieval context (Tulving's encoding specificity): typed notes gain appliesTo, path globs; a Claude Code hook on file reads and edits matches them locally and injects that path's gotchas and procedures, each once per session, the 'already injected' record kept in a cache file apart from storage.json.

(2) Consolidation, episodic to semantic: when a task with handoffs and no typed note is completed, set_state's reply carries 'consolidate': {handoffs, typedNotes}, and an MCP prompt consolidate asks the agent to extract decisions and gotchas from them. Nothing is written on its own.

(3) Reconsolidation, validity that ages: ekko --confirm &lt;id> records verifiedAt; a gotcha unconfirmed for N days, or whose appliesTo files changed much since (git log), shows in the prime as possibly stale.

(4) Prospective memory, event triggers: waiting --until tag:X, date:D or task:&lt;uid> (another project), checked locally by prime and next, which say the condition was met. Never cmd: conditions, at least not over MCP.

(5) Episodic memory, sessions as entities: each write stamped with its session (provenance, not capture); ekko --episodes lists sessions with the items they touched, their handoff and their commits, through an 'Ekko:' commit trailer; the spine of a --docs timeline.

(6) Procedural memory (ACT-R's proceduralization): a procedure may carry a run block that ekko --run &lt;id> executes, CLI only at first, over MCP only as a tool with its own permission, like force_state.

(7) Salience without writes on read: importance from structure (tasks attached, handoffs citing it by id, confirmations), not read counts, to order the prime.

MVP order proposed there: appliesTo with hook injection, consolidation at close, waiting triggers, verifiedAt; sessions and --run later, with --docs. Gains claimed: fewer repeated mistakes (the most tangible), knowledge outliving its task, trustworthy memory, lower cost per session, less supervision, an account of the work at the end. Costs named: fields, error codes, tests, noise from broad globs, more reliance on undocumented Claude Code behaviour, discipline still needed. It suggested the user's migration as the experiment: a week or two as is, then one feature at a time.

### <a id="340"></a>340. ANALYSIS, session dccf828e, 2026-09-22. The memory types are a good lens (they match CoALA's working, episodic…

ANALYSIS, session dccf828e, 2026-09-22. The memory types are a good lens (they match CoALA's working, episodic, semantic and procedural memory; Sumers et al. 2023), but Claude Code already does two of the seven (note above), the token gains claimed contradict what this board measured (ekko's replies are 1 to 2% of the bill; the lever is segmentation: notes [163](../decisions.md#163), [286](267.md#286), [319](312.md#319)), and the ideas worth building are the ones Claude Code cannot do.

(1) appliesTo: right idea, native transport. What ekko would add: retrieval on an error -- a PostToolUse on Bash whose output holds a gotcha's literal cue (e.g. 'relation does not exist') injects it, encoding specificity at its purest, matched as a literal substring (no regex, no ReDoS); retrieval on edits, not only reads; the note's life cycle. Design: PostToolUse additionalContext; a cap per event (\~2 notes, 1,500 characters); once per session and per agent; paths relative to the git root (a worktree's absolute paths differ); cat and sed through Bash escape path cues. Cheaper first: ekko generates .claude/rules files from its notes and the native loading injects them (reads only, and in the repo tree, so gitignored).

(2) Consolidation: good (complementary learning systems, McClelland et al. 1995; Generative Agents' reflection, Park et al. 2023), but the trigger is too narrow. On this board: 93 done tasks, 5 with a handoff, 3 of those with no typed note; 36 done tasks with notes and none typed; 26 of 205 notes typed (18 decisions, 6 gotchas, 2 procedures). Handoffs are not lost, only no longer surfaced (availability against accessibility, Tulving and Pearlstone 1966): count plain notes too, and let the prompt answer that nothing is worth keeping.

(3) verifiedAt: answers a failure seen here (184 grew to 9,125 characters and misled a session; 168, 169, 170 and 184 were stashed as stale on 2026-09-22). Prefer staleness by event, appliesTo files changed since the confirmation (git log), to an arbitrary N days; auto memory records only when a note was written.

(4) Waiting triggers: right concept (Einstein and McDaniel 1990; Taskwarrior's wait: and scheduled:), little evidence: 2 waiting tasks in this board's life (220, 267), both on outside events no tag, date or task condition can check, and task:&lt;uid> on the same board is blocked_by. date: is cheap and useful; the rest waits for use.

(5) Sessions as entities: ranked last there, first here, as the substrate of owners (264), 261 and 262. CLAUDE_CODE_SESSION_ID is already in each server's environment (note [289](264.md#289)): record the session per revision in the journal. The 'Ekko:' commit trailer links commits to items deterministically, which would have kept 13 notes from saying 'uncommitted' after their commits. Design with 264.

(6) --run: not as proposed. The board is written by agents, so a stored command is a persistent vector for injected instructions (it would need approval by content hash, as direnv allow does); the board has no history (277), a worse home for code than the repo; procedural memory already has a native home in skills and scripts (Voyager's skill library, Wang et al. 2023). Instead, a procedure names the script or skill to run.

(7) Structural salience: good and read-pure. In-degree (tasks attached, 'note [163](../decisions.md#163)' citations, confirmations) is cheap; mix it with recency and supersession against rich-get-richer.

GAINS. Every injected token costs 2 once and 0.1 per later call, so injection must stay tight. The large plausible gain is quality, fewer repeated mistakes, and it is unmeasured: an eval with planted gotchas under four arms (no memory, gotcha in the prime, injected by path, injected by error), where \~20 runs per arm detect a trap rate going from 50% to 10% (Fisher, alpha 0.05, power \~0.9). It spends quota: design it with the user, as 259.

ORDER suggested: session provenance with 264; the planted-gotcha eval, prototyped on native rules with no ekko code; if it pays, error and edit triggers in ekko; validity tied to code changes; the consolidation hint counting plain notes; --until date:; structural ranking; not --run. First, the user's decision on auto memory.

### <a id="445"></a>445. 406(a) BUILT, session 81ba8737, 2026-09-23, in \~/NixOS (taken by auto-commit e9612d2): a PreToolUse hook on Bash in…

406(a) BUILT, session 81ba8737, 2026-09-23, in \~/NixOS (taken by auto-commit e9612d2): a PreToolUse hook on Bash in usr.claude-code's --settings, so both profiles. scripts/claude-code-pgrep-guard.py refuses a pgrep or pkill that has -f and not -A. procps-ng 4's -A (--ignore-ancestors) leaves out the shell running the command (checked: pgrep -af X finds its own shell, pgrep -afA X finds nothing, inside $(...) too), so the refusal names the one flag to add, and a call with -A or without -f runs.
