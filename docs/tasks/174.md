### <a id="213"></a>213. TEST RUN 2026-09-21, Claude Code 2.1.278, interactive, with the user at the keyboard: an @ mention of an MCP resource…

TEST RUN 2026-09-21, Claude Code 2.1.278, interactive, with the user at the keyboard: an @ mention of an MCP resource WORKS. The probe server (now evals/claude-code/probe_server.py, run with --strict-mcp-config) offered item://93 through resources/list. Typing @probe autocompleted probe:item://93. On send, the client called resources/read {uri: item://93} (in the probe log, after initialize, tools/list, prompts/list, resources/list and resources/templates/list), and attached the body to the prompt: the model quoted RESOURCE_BODY_J6H without calling a tool, plus a line from Claude Code saying not to read the resource again unless it may have changed. Print mode (note [167](../notes.md#167)) never expands a mention; interactive does. ### <a id="214"></a>214. SECOND TEST 2026-09-21, same setup, the probe now also serving a template item://{id} from resources/templates/list…

SECOND TEST 2026-09-21, same setup, the probe now also serving a template item://{id} from resources/templates/list while resources/list still names only item://93. Autocomplete offered both, as 'probe:item:// – an item by id' and 'probe:item://93 – item 93'. A hand-typed @probe:item://5 attached NOTHING: the model saw plain text, and the log has no resources/read for it. @probe:item://93 attached as before. So Claude Code resolves a mention only for a URI that resources/list returned, and a template does not make other ids mentionable. It is untested whether picking the template entry in autocomplete and typing an id resolves. CONSEQUENCE FOR THE DESIGN: an item is mentionable only if it was in the list the client last read. That list is read once, at connect. A board's new items need the server to send notifications/resources/list_changed, and whether Claude Code re-reads the list on that notification is untested.

*Note · 2026-09-21*

### <a id="215"></a>215. THIRD TEST 2026-09-21, same setup: list_changed WORKS. The probe advertised resources.listChanged. At first its list…

THIRD TEST 2026-09-21, same setup: list_changed WORKS. The probe advertised resources.listChanged. At first its list named only item://93 and autocomplete showed only that. A tools/call to longtool added item://5 and sent notifications/resources/list_changed right after the reply. The log shows the client immediately called resources/list and resources/templates/list again. Autocomplete then offered item://5, and picking it and sending attached the body: the client called resources/read {uri: item://5}, and the model quoted it. So a server can keep what is mentionable current by sending list_changed after the list grows. It needs no restart and no /mcp.

After every message, Server::list_changed compares the board's revision and then the list with what the client last read, and sends notifications/resources/list_changed when the list changed; only once the client has read the list.
