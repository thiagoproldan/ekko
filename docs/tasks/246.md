### <a id="251"></a>251. Done in the working tree 2026-09-21, not committed yet. Item::unknown is a #[serde(flatten)] BTreeMap&lt;String, Value> at…

Done in the working tree 2026-09-21, not committed yet. Item::unknown is a #[serde(flatten)] BTreeMap&lt;String, Value> at the end of Item: fields this version does not know are kept with their values and written back after the known ones, in name order. Counters::unknown does the same for counters.json, which every write rewrites. Counters lost Copy, so set_counters takes &Counters. The project registry and project.json, written only by init and destroy, are not covered. A BTreeMap, not serde_json::Map: preserve_order makes that an IndexMap with a hasher per item. On a cold --prime of 5,000 items (2.7 MB), over 40 alternating runs, the medians were 21.7 ms for ffbbf19, 22.8 ms with the IndexMap and 22.1 ms with the BTreeMap. TESTS: item::a_board_with_nothing_unknown_is_written_back_byte_for_byte, whose fixture came from the 0.10.2 binary plus phase and handoff by hand, and passed before the change too; item::fields_from_a_later_version_survive_a_read_and_a_write; ekko::fields_from_a_later_version_survive_this_versions_writes (the item changed, an item left alone, and the archive via --clear); storage::counters_keep_what_a_later_version_added. On a copy of this very board, --star by ffbbf19 and by the new build gave the same storage.json apart from updatedAt, and the same counters.json. cargo test 265, clippy clean, semantics 27 of 27, scale prime sizes unchanged. The readme's 'Locating the data files' gained a paragraph: from v0.11.0 on, unknown fields are kept, and versions before it still drop them.
